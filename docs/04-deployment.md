# 4. Ручная установка на собственном стенде

Это runbook администратора, не исполняемый installer. Перед любым действием — отдельный IPv4 SSH, консоль, baseline служб и только узкие резервные копии. На общем сервере сначала согласуйте интеграцию с действующим менеджером firewall. Не меняйте Docker, nginx, SSH, Netplan или глобальную политику ради VPN.

## Закрытые файлы и экземпляры

Создайте вне Git root-only `/etc/awg31` (0700), файлы `direct.conf`, `relay.conf` (0600); бинарники в `/opt/awg31/bin/` (0755). Адреса замените согласно inventory. Серверные `.conf` содержат **только поля awg setconf**, без `Address`, `DNS`, `MTU`, `PostUp` или клиентского `AllowedIPs=0/0`. Клиентские full-tunnel профили не являются серверными конфигами.

Подготовьте `examples/awg-server.conf.example` дважды: разные private keys, listen ports, параметры экземпляра, peer keys и адреса. Генерация ключей — [официальными tools](05-clients.md). Протокольный блок из `examples/protocol.conf.example` после закрытого заполнения вручную вставьте в `[Interface]` **до `[Peer]`** на сервере и соответствующих клиентах. Не используйте один блок для двух экземпляров. Этот файл — фрагмент, а не отдельный конфиг.

## Фильтрация до поднятия интерфейсов

`examples/exit.v4.rules.example`, `exit.v6.rules.example`, `relay.v4.rules.example` — форматы iptables-restore, **только добавочные именованные цепочки и переходы**. Здесь нет `-F` для глобальных цепочек или изменения policies. Их нельзя применять обычным restore: без `--noflush` можно удалить другие правила. Перед ручным использованием:

1. Замените WAN_IF, адреса, подсети; убедитесь, что имена цепочек свободны. Это одноразовые шаблоны, повторное применение не идемпотентно.
2. Проверьте порядок относительно UFW/nftables/Docker/cloud firewall. Разрешение одной цепочки не отменяет DROP другой независимой base chain. Не смешивайте legacy и nft backend.
3. На изолированном стенде выполните `iptables-restore --test --noflush < ...` и аналогичный `ip6tables-restore`; это проверка ядром, которой нет в обычном Python валидаторе. Затем примените вручную `--noflush`. Не запускать на production без разбора.
4. Вход Direct по IPv6 закрыт; вход Relay по IPv4 закрыт; по IPv6 только source входного VPS → точный backend. Realm принимает только свой IPv4:порт. В ingress цепочках первым проверяется вход с AWG интерфейсов, чтобы клиенты не обращались к локальным UDP listeners.
5. INPUT клиентов DROP, кроме необязательного TCP443 к точному EXIT4. Включение этого исключения разрешает все HTTPS vhosts данного IP с прежней auth. Оставляйте закомментированным, если публичный HTTPS на выходном VPS не нужен. TCP80/SSH и остальные локальные адреса не разрешаются.
6. FORWARD разрешает только исходящий публичный IPv4 из собственной подсети в WAN и ответы ESTABLISHED,RELATED; частные, link-local, multicast и специальные сети блокируются перед ACCEPT. Добавьте все иные локальные/провайдерские подсети, если они есть. IPv6 INPUT/FORWARD клиентов DROP, NAT66 отсутствует. Прямое межклиентское и межинтерфейсное продвижение не разрешено.

IPv4 NAT требует `net.ipv4.ip_forward=1`. На новом VPN VPS администратор отдельно проверяет/включает это с собственной persistent sysctl записью и планом отката. На общем хосте forwarding может уже использоваться другими службами: не переключать его глобально автоматически и не выключать при удалении VPN. IPv6 forwarding для этой архитектуры не нужен, существующее значение не менять. При смене firewall повторять отрицательные проверки.

**Персистентность:** интегрируйте только свои правила в фактический менеджер firewall, до AWG. Для нового выделенного VPS приложены два **ручных шаблона**: `systemd/vpn31-filter-exit.service.example` и `vpn31-filter-relay.service.example`. Установить на каждом VPS только соответствующий вариант под именем `vpn31-filter.service`; paths/порядок относительно firewall manager проверить отдельно. Заполненные rules копируются root-only без `.example` в `/etc/awg31/` или `/etc/realm31/`. Unit сначала вызывает kernel `--test --noflush`, затем загружает только собственные добавочные цепочки. Его `enable` обеспечивает загрузку после reboot; reboot здесь не проверен.

Загрузчик намеренно отказывается при уже занятых chain names, не является повторно применимым. **Не** включайте его одновременно с другой системой, сохраняющей те же цепочки. После частичной ошибки загрузки сначала ручная инвентаризация/точечный cleanup собственных добавлений, не повторный flush. `ExecStop` не удаляет правила: stop сохраняет фильтрацию, а `BindsTo` останавливает зависимые VPN/Realm. Для обновления правил на работающем VPS нужен отдельный точечный план; restart этого oneshot не является таким планом. На общем VPS предпочтительна интеграция в существующий менеджер с той же логикой и именем gating-unit. Пока локальная `vpn31-filter.service` не подготовлена, AWG/Realm не запускаются. Не сохраняйте весь ruleset и не восстанавливайте чужие правила при rollback.

## systemd AWG

Шаблон `systemd/awg31@.service.example` адаптируйте в `awg31@.service`. Drop-ins direct и relay содержат адреса/MTU. Предварительная проверка файлов без отображения содержимого:

```sh
systemd-analyze verify /etc/systemd/system/awg31@.service
```

Drop-ins установить как `awg31@direct.service.d/override.conf` и `awg31@relay.service.d/override.conf`; без них unit содержит защитные заглушки. `$$` в shell строках — обязательное экранирование systemd, не заменять на `$` в unit. Unit запускает официальный Go foreground и затем через ExecStartPost ожидает UNIX socket, выполняет `awg setconf`, назначает **только адреса интерфейса** и включает MTU1280. В нем нет изменения default route. Результат awg подавлен, чтобы ошибки парсера не отправили приватные значения в journal. После подготовки правил и файлов — `systemctl daemon-reload`, затем `systemctl enable --now vpn31-filter.service`, `systemctl enable --now awg31@direct awg31@relay`. Это запуск новых служб, не рестарт сети. Убедитесь в реальном bind `ss -lun`, IPv4/IPv6 правилах, адресах, IP forwarding и автозапуске.

## Realm на входном VPS

`/etc/realm31`0700, `realm.toml`0600 из примера. Один числовой backend IPv6, source IPv6 явно задан; DNS fallback на IPv4 backend отсутствует. `no_tcp=true`, `use_udp=true`, никакого приема proxy headers или произвольных destinations. Realm не заменяет firewall и не предоставляет криптографическую авторизацию.

Бинарник `/opt/realm31/bin/realm`; `systemd/realm31.service.example` использует DynamicUser и LoadCredential, без NET_ADMIN. После готовности собственного firewall и проверки unit — enable/start локальной vpn31-filter.service и затем только realm31. Проверьте UDP frontend, отсутствие TCP frontend, source/destination IPv6 по заголовкам. Не открывайте IPv4 backend Relay на выходном VPS.

## При ошибке

Не выключайте общую защиту. Остановите только свои новые units (с интерфейсом исчезнут его адреса), удалите только точные добавленные jumps и собственные цепочки по [плану отката](07-operations.md). Не меняйте уже работающий IPv6 и другие службы. Перед выдачей профилей обязательны реальные испытания.
