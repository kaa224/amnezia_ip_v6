# 6. Приемочные проверки

Проверить **каждый** из четырех профилей на своем устройстве; Direct и Relay независимо. Не приписывать результаты другому профилю. Перед испытанием отключите другие VPN/proxy и исключения split tunnel, зафиксируйте baseline WAN IPv4/IPv6/DNS, не публикуя его. Не проводить нагрузочные тесты.

| Проверка | Ожидаемый результат |
|---|---|
| Handshake + счетчики передачи | Новая сессия на правильном экземпляре; маленький двусторонний обмен |
| DNS A собственного public hostname | Адрес соответствует inventory |
| DNS через tunnel resolver | Ответ получен, DNS leak test соответствует политике Cloudflare |
| Обычный внешний HTTPS | Валидный TLS, HTTP успешен |
| Внешний IPv4 | Выходной VPS для обоих путей |
| Публичный HTTPS выходного VPS с SNI | Успех, если включено точное исключение 443 |
| Внутренний IPv6 / внешний IPv6 тест | Нет выхода через провайдера клиента; серверный DROP возрастает |
| TCP22/80, внутренние порты, другие local IP | Недоступны через VPN |
| RFC1918/ULA/link-local/Docker/metadata | Недоступны из VPN, проверить все реальные подсети inventory |
| Вход к backend Relay | Только разрешенный source IPv6; IPv4 закрыт |
| Переподключение и смена сети | Результаты отдельно для Wi-Fi/сотовой сети |
| Аварийный разрыв | Отдельно подтвердить kill switch, DNS и IPv6 поведение |

DNS тестируйте из туннеля, например `nslookup example.com REPLACE_DNS_PRIMARY`; браузерный DoH может выбирать другой resolver, поэтому отдельно проверить его настройки. На Windows `curl.exe -4 --max-time 10 https://example.com/`, `curl.exe -6 --max-time 10 https://example.com/` (второй должен не иметь IPv6 выхода). [IPLeak](https://ipleak.net/) полезен для проверки WebRTC, DNS и дополнительных адресов; не публикуйте скриншоты с адресами. WebRTC mDNS/LAN кандидаты не равны публичной утечке — сравнивайте с baseline. На iOS дополнительно учтите Private Relay и собственные DNS-профили: документируйте настройки, не делайте вывод только по одному сайту.

## Диагностика собственного HTTPS

На клиенте с подключенным профилем, после замены адреса и hostname:

```sh
curl --max-time 10 --resolve example.com:443:192.0.2.10 https://example.com/
```

SNI и верификация сертификата остаются включены. Если внешний HTTPS работает, а этот нет: на сервере `ip route get 192.0.2.10 from 203.0.113.2 iif awg31d` покажет local route; сравните только счетчики собственных INPUT цепочек до/после одной попытки. Это локальный INPUT, не FORWARD/NAT. Не открывайте все local адреса. Опциональный ACCEPT к точному EXIT4:443 разрешает все vhosts этого IP, не отменяя HTTP auth; если source ACL приложений блокирует — не ослаблять его автоматически. 80 для прямого HTTPS не нужен.

## Серверные тестовые peer

Для нового проекта требуется отдельный третий тестовый узел или изолированный netns/userspace netstack, не меняющий default route тестового хоста. Выпускать временные уникальные peer; заполнять их параметры только закрыто. Внешний участок клиент → frontend тестировать **из другой сети**: запуск на самом Realm его не проверяет. Проверить DNS/HTTPS/IP, затем отрицательные доступы, удалить peer live/persistent, процессы, namespace и секретные файлы. Этот репозиторий не предоставляет сетевой mutating test runner.

Для транспорта Realm достаточно краткого захвата **только метаданных** по точным src/dst IPv6 и UDP порту, без `-A/-X` и без pcap с payload; еще безопаснее — счетчики правил. Даже заголовки содержат реальные IP, не помещать raw output в Git. Сопоставьте route get и отсутствие IPv4 backend. Offload GRO/GSO может давать oversized capture records, это не доказательство размера кадра на линии.

MTU1280 — исходная величина. Вычислите worst-case `inner MTU + padding alignment + AWG data overhead + protocol additions + outer IPv6(40) + UDP(8) <= path MTU`; учитывайте максимальные значения диапазонов, S4 и trailers по pinned исходнику. Проверяйте также handshake datagrams. Поскольку параметры-заглушки не заданы, проект **не утверждает**, что этот бюджет уже соблюден. Проверить PMTU, короткие DF-пробы, IPv6 fragmentation/reassembly counters и захват фрагментных заголовков без вывода payload. Уменьшайте MTU согласованно, не отключайте глобально offload или ICMPv6. Без ICMPv6 Packet Too Big/ND нормальная IPv6 связность может нарушиться; не заменяйте политики хоста.

После включения проверить внешний доступ к публичному HTTPS, отдельный административный SSH и существующие приложения/времена запуска контейнеров. Перезагрузка — отдельная согласованная проверка автозапуска, не равна `is-enabled`.
