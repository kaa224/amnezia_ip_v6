# 7. Обслуживание и откат

Сохраняйте закрытый inventory и manifest. В журнал проекта заносите только даты, версии, результаты и redacted изменения. Никогда не коммитьте файлы профилей, UAPI dumps, ключи, PSK, индивидуальные параметры, QR, raw firewall snapshots или журналы подключений.

Безопасные команды состояния на соответствующем узле:

```sh
systemctl is-active awg31@direct awg31@relay
systemctl is-enabled awg31@direct awg31@relay
ip -br link show awg31d
ip -br link show awg31r
systemctl is-active realm31
```

На хостах смотреть `ss`, IPv6 route get и счетчики **своих** цепочек локально, не публиковать raw outputs. Различайте daemon active, новый handshake и настоящий DNS/HTTPS. Если сломан только Relay — frontend firewall/Realm/IPv6/backend; если оба — общий выходной VPS, DNS/NAT/forward. Если только свой сайт — local route/INPUT/SNI/auth. Ошибка ключей — не причина переписывать маршрутизацию.

Перед обновлением зафиксируйте commit/digest, подготовьте проверенный официальный бинарник рядом, копию **только изменяемых файлов**, сохраните независимый SSH и точный rollback. Не заменяйте бинарник работающего процесса in-place. Переключайте один новый экземпляр в согласованное окно, проверяйте реальные подключения, положительные и отрицательные тесты, затем второй. Не рестартовать Docker или сеть. Не выполнять `awg showconf` / `syncconf` с выводом полного файла в монитор. Доступ к закрытым резервным копиям — root-only; удаление следов из Git не отзывает скомпрометированный ключ.

## Rollback компонентов на собственном развертывании

1. Сначала отозвать/закрыть выдаваемые профили, остановить только свои `awg31@direct`, `awg31@relay`, `realm31`. Стоп AWG удаляет только его TUN интерфейс, не default route хоста.
2. Удалить точные jumps к PV31* в INPUT/FORWARD/POSTROUTING, **по аргументам, не по номеру строки**. После удаления ссылок очистить и удалить только собственные именованные цепочки. Нельзя глобальный flush или восстановление чужого ruleset. Разные таблицы и семейства обрабатываются отдельно.
3. Отключить автозапуск только собственных units, удалить только добавленные drop-ins/configs/binaries, затем daemon-reload. Не удалять общий каталог IPC другого проекта. Сначала убедиться, что из двух экземпляров ни один больше не использует общий новый каталог.
4. Если обновлялся файл — восстановить его собственную резервную копию с правильными правами и прежний бинарник, затем запустить только затронутый экземпляр и повторить проверки.
5. Не менять IPv6 default, Netplan, SSH, nginx, Docker и чужие правила. Не выключать ip_forward, если его использует другая служба. Удалять только собственную sysctl запись после отдельной оценки текущего forwarding.

Точные команды удаления берутся из **фактически установленного** закрытого rules manifest. Пример для необязательного HTTPS Direct (адреса документационные, на реальном сервере заменить):

```sh
iptables -w 5 -D PV31D_H -i awg31d -s 203.0.113.0/26 -d 192.0.2.10/32 -p tcp --dport 443 -j ACCEPT
```

Для снятия всей конфигурации используйте точные `-D INPUT -i awg31d -j PV31D_H`, `-D FORWARD -i awg31d -j PV31D_O`, `-D FORWARD -o awg31d -j PV31D_I`, `-t nat -D POSTROUTING -s 203.0.113.0/26 -o REPLACE_WAN_IF -j PV31D_N`, аналогичные Relay и IPv6/port цепочки из ваших файлов. Потом только `-F PV31...` и `-X PV31...` для освобожденных цепочек, не `iptables -F`. Не пытайтесь применять шаблонный rollback к неизвестному работающему серверу.

## Миграция со старой версии

Старую рабочую версию не удалять до отдельного подтверждения переключения пользователя и проверки **обоих** новых путей. Вывод из эксплуатации — отдельное окно: точный список старых units, peers/configs/секретов, binary paths, ports, chains; проверить отсутствие общих зависимостей, остановить и удалить только старые компоненты, затем повторить новый Direct/Relay, HTTPS, DNS, IPv6, SSH и health. Настоящая задача этот план не выполняет.
