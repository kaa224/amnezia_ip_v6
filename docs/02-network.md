# 2. IPv6 и связность

Сначала определите источник конфигурации **хоста**, например cloud-init → Netplan → systemd-networkd, NetworkManager или ifupdown. Не редактируйте сгенерированный файл вместо источника. Read-only команды:

```sh
ip -br address
ip -4 route show
ip -6 route show
ip -6 neigh show
networkctl status
ss -lun
```

Не публикуйте эти выводы без редактирования. Получите в панели, официальной инструкции или службе поддержки провайдера: назначенный адрес и префикс (в том числе /128), точный gateway, интерфейс, необходимость onlink/host route, DHCPv6/RA, MTU, способ сохранения конфига. **Сосед с окончанием ::1 не доказывает, что он шлюз.**

Официальные примеры: [FirstVDS: дополнительные IPv4/IPv6](https://firstvds.ru/technology/kak-dobavit-ip-na-server), [особенности VPU](https://firstvds.ru/technology/setevye-nastroyki-v-klasterakh-s-tekhnologiey-vpu), [Netplan routing](https://netplan.readthedocs.io/en/stable/netplan-yaml/). Инструкции различаются между провайдерами и кластерами; эти ссылки не подтверждают gateway вашего VPS.

Если маршрута нет, остановите установку VPN. Изменение IPv6 — самостоятельная операция: открытый IPv4 SSH, новая проверенная IPv4 сессия, консоль, копия только изменяемого файла, заранее проверенный автоматический rollback. Сначала временный маршрут с **подтвержденным** gateway и dev; onlink только по параметрам провайдера. После проверки — минимальный отдельный файл фактического менеджера сети и изолированная генерация Netplan через `--root-dir`, без общего рестарта сети. Статическая проверка не доказывает переживание reboot. Не переносите чужой default gateway из примера и не затрагивайте IPv4.

## Двунаправленные проверки

После замены документационных адресов выполните на входном VPS:

```sh
ip -6 route get 2001:db8:10::10 from 2001:db8:20::20
ping -6 -c 3 -I 2001:db8:20::20 2001:db8:10::10
ssh -6 -o BatchMode=yes exit-vps true
```

И на выходном VPS — обратный route get, ping к `2001:db8:20::20` с source `2001:db8:10::10` и SSH к заранее настроенному alias входного узла. Для проверки source нужны реально назначенные адреса. SSH alias должен выбирать правильный IdentityFile и IPv6 Hostname; host key сверяйте через доверенную консоль, `ssh-keyscan` сам по себе не удостоверяет ключ. Не отключайте StrictHostKeyChecking. Ошибка авторизации SSH не означает сетевой отказ IPv6.

Проверьте `curl -6 --max-time 10 https://example.com/` на обоих узлах и A/AAAA выбранных тестовых доменов. Проверяйте реальный UDP обмен короткой сессией AWG после установки: UDP scan без ответа ничего не доказывает. Временные слушатели — только на свободных высоких портах, с ограничением peer и обязательным удалением; пакеты/нагрузку не генерировать массово. При блокировке локализуйте host firewall / cloud firewall / путь провайдера, не выключайте firewall ради проверки.
